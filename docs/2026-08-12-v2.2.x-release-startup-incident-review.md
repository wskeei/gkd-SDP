# v2.2.x 正式版启动崩溃复盘与修复 Review

日期：2026-08-13
范围：v2.2.0、v2.2.1、v2.2.2 的 `gkdRelease`/`playRelease` 混淆 APK

## 结论

这是一个 P0 发布阻断问题：v2.2.x 正式 APK 在首次启动时于 `Application.onCreate` 崩溃，用户看到的表现是“安装后打开卡住/立即回到桌面”。v2.1.1 正式 APK 可启动。问题不是手机数据损坏，也不是单一 OEM 行为。

根因链路为：

1. `DbSet` 为每个 Room DAO 建立 Java 动态代理，以便把 suspend DAO 写操作纳入备份互斥门。
2. 原实现通过 `delegate::class.java.interfaces` 发现 Room 生成实现类的接口；这依赖运行时接口元数据。
3. R8 混淆后会移除/重写 Room 生成实现类及 DAO 接口的运行时类型信息；即使调用方显式传入接口 `Class`，未保留的 `@Dao` Kotlin interface 也可能被优化成不能用于 Proxy 的类型。
4. `App.onCreate -> initSubsState -> DbSet.getSubsItemDao -> gateRoomDao` 的 `require(...isInterface)` 抛出 `IllegalArgumentException: Failed requirement`。

受影响版本均可由相同堆栈复现：

```text
Caused by: java.lang.IllegalArgumentException: Failed requirement
  at li.songe.gkd.sdp.backup.GatedRoomDaoKt.gateRoomDao(GatedRoomDao.kt:20)
  at li.songe.gkd.sdp.db.DbSet.getSubsItemDao(AppDb.kt:226)
  at li.songe.gkd.sdp.util.SubsStateKt.initSubsState(SubsState.kt:424)
  at li.songe.gkd.sdp.App.onCreate(App.kt:276)
```

回归来源是 `96adf3f8`（引入 `GatedRoomDao` 的数据/远程接口加固提交）；该提交后的 JVM 合约测试没有覆盖 R8 产物。

## 为什么旧门禁漏掉了

- CI 只 assemble 了 release，没有安装并启动 minified APK。
- 原 macrobenchmark 目标是 `gkdNonMinifiedRelease`，不能证明 R8 产物启动。
- `GatedRoomDaoTest` 使用普通 JVM synthetic delegate；该 delegate 保留接口元数据，无法模拟 Room + R8 的运行时类型变化。
- 旧测试只验证“代理行为”，没有验证 `Class.isInterface` 与 `Proxy.newProxyInstance` 在 release dex 上的事实。

## 已执行的修复

### 1. 移除实现类接口反射推断

`gateRoomDao` 改为接收显式接口类型：

```kotlin
gateRoomDao(SubsItem.SubsItemDao::class.java, db.subsItemDao())
```

`AppDb.kt` 的所有 DAO getter 均使用其声明的 `@Dao` 接口 class literal，代理缓存、suspend gate、失败传播、取消和默认方法语义保持不变。

### 2. 保留动态代理所需的接口

`app/proguard-rules.pro` 增加最小规则：

```proguard
-keep @androidx.room.Dao interface *
```

这不是把整个 Room 或业务实现类全部 keep，而是只保留运行时 `Proxy` 必须使用的 DAO 合约。

### 3. 增加回归测试和真实 APK smoke

- JVM 测试新增非接口 token 拒绝用例，并继续覆盖同步、异步、异常、取消、代理缓存及 transaction-like 默认方法。
- `scripts/smoke-test-release-apk.sh` 对真实安装 APK 执行 clean install、冷启动、进程存活、resumed activity 和本包 FATAL/ANR 检查。
- `scripts/run-release-apk-smoke-emulator.sh` 为 API 26/API 35 创建临时模拟器，CI/Nightly 对 `gkdRelease` 和 `playRelease` 都执行上述检查。
- workflow 显式安装 API 26/API 35 x86_64 system images，避免 smoke runner 因 runner 镜像差异被跳过或误报。

## 已完成验证

- `:app:testGkdDebugUnitTest --tests '*GatedRoomDaoTest'`：通过。
- `:app:assembleGkdRelease :app:assemblePlayRelease`：通过，且实际执行 R8。
- API 35 模拟器 clean install + cold start：`gkdRelease` 通过，`playRelease` 通过。
- 修复前 API 35 minified APK：按相同脚本复现上述 `Failed requirement` 崩溃。
- 已审查 `App.onCreate` 可达的反射/断言路径；目前没有第二个可由真实 release 产物复现的启动阻断问题。其余 `require` 位于备份数据校验等输入边界，不在启动调用链，不作无证据修改。

## 发布与后续修复步骤

1. 在功能修复 PR 中合并上述代码、规则、测试、smoke runner 和本复盘文档。
2. 通过 Python 合约、selector JVM、app unit、两 flavor lint、两 flavor release assemble、security report、API 26/API 35 minified smoke 以及 `git diff --check`。
3. 以 `versionName=2.2.3`、未占用且大于历史值的 `versionCode` 创建发布 PR；执行 release metadata/update manifest 验证。
4. 合并发布 PR 后，在已通过 main CI 的合并提交创建 annotated `v2.2.3` tag；只推送新 tag，不移动历史 tag、不替换历史资产。
5. 核对 Draft Release 的 APK 包名、版本、签名、SHA-256、provenance/attestation，并用发布工作流生成的真实 minified APK 再执行 API 35 smoke；通过后发布 stable/latest。
6. 在 v2.2.0、v2.2.1、v2.2.2 的 Release notes 增加“启动崩溃，请升级到 v2.2.3 或更高版本”的警告，保留原资产。
7. 真机/OEM 后续验收：从 v2.2.2 升级安装而不清除数据，验证 Room/store 配置、锁定状态、订阅、无障碍/Overlay 权限和首次启动；这些项目不能由模拟器结果代替。

## 未执行项

当前环境没有用户的实体手机和 OEM 测试矩阵，因此没有声称真机、厂商 ROM、无障碍服务恢复或从 v2.2.2 的数据保留升级已通过。发布后应按 `docs/testing/release-smoke-checklist.md` 记录设备型号、Android 版本、安装来源和结果。
